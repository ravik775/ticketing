# Kubernetes platform (k3s/k3d, NetworkPolicies, pod security, cert-manager)

## Concepts you must own

* **Workloads:** Deployment (stateless, rolling updates), StatefulSet (stable identity + per-pod PVC),
  Job/CronJob; **Services:** ClusterIP, NodePort, LoadBalancer, headless (`clusterIP: None`).
* **Probes:** startup (slow boot), readiness (in/out of Service endpoints), liveness (restart).
* **Resources & QoS:** requests drive scheduling, limits cap usage; Guaranteed / Burstable /
  BestEffort; memory over limit → OOMKilled; CPU over limit → throttled.
* **NetworkPolicy:** pod-level L3/L4 firewall enforced by the CNI. Once a pod is selected by a policy
  of a type (Ingress/Egress), only allowed traffic passes. Within one `from`/`to` element,
  `namespaceSelector` + `podSelector` are **AND**; separate elements are **OR**.
* **Pod security:** `securityContext` (non-root, no privilege escalation, drop capabilities, seccomp,
  read-only root FS), Pod Security Standards (privileged / baseline / restricted), service-account
  token automount.
* **Secrets:** base64-encoded, not encrypted by default (enable etcd encryption / KMS); RBAC on `get secrets`.
* **cert-manager:** Issuer/ClusterIssuer, Certificate → Secret (`tls.crt`, `tls.key`, `ca.crt`),
  renewal at 2/3 of lifetime by default, `rotationPolicy: Always` (new key on renewal).
* **Kustomize:** resources, generators (ConfigMap/Secret), hash suffixes that trigger rollouts.
* **Scaling & availability:** HPA, PodDisruptionBudget, anti-affinity / topology spread, rolling update
  `maxSurge/maxUnavailable`.

## Questions

### Q1. Read this policy element and tell me exactly what it allows. ★★★★
**30-second headline:** Both selectors in one element means AND (kong pods in gateway); as separate list items it would be OR, a classic over-permissive mistake.
**Weak answer (what fails):** Reading it as OR.
```yaml
ingress:
  - from:
      - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: gateway}}
        podSelector: {matchLabels: {app: kong}}
```
**Strong answer:** One element with both selectors = **AND**: pods labelled `app=kong` **in** the
`gateway` namespace. If they were two list items (`- namespaceSelector…` and `- podSelector…`), it
would be **OR**: *any* pod in `gateway` **or** any `app=kong` pod in the *policy's own* namespace: a
classic over-permissive mistake. Also: labels are attacker-controllable if someone can create pods in
that namespace, so RBAC on pod creation is part of the policy's strength.

### Q2. Why do the default-deny policies need an explicit DNS egress rule, and what breaks if you forget it? ★★★
**30-second headline:** Egress default-deny blocks DNS, so every service name fails to resolve and looks like an outage; allow CoreDNS explicitly.
**Weak answer (what fails):** Not mentioning DNS at all.
**Strong answer:** Egress default-deny blocks UDP/TCP 53 to CoreDNS; every service name lookup fails →
connection errors that look like the target is down. The allow targets `kube-system` pods with
`k8s-app: kube-dns`. Follow-up: NodeLocal DNSCache changes the destination (link-local IP), so the rule
must change with it.

### Q3. Which traffic does NetworkPolicy *not* govern in this cluster? ★★★★★
**30-second headline:** port-forward/exec, hostNetwork pods, node-to-pod probes, the Kubernetes API (RBAC instead) and anything L7; that's why mTLS, JWT and the WAF exist.
**Weak answer (what fails):** "NetworkPolicy blocks all traffic."
**Since implemented:** exec/port-forward are now detected via the Kubernetes audit log in the SIEM.
**Strong answer:** `kubectl port-forward`/`exec` (streamed through the kubelet into the pod's network
namespace), `hostNetwork` pods, kubelet probes from the node (most CNIs allow node → pod), traffic to
the Kubernetes API from pods (governed by RBAC + token, and we removed tokens), and anything at L7
(NetworkPolicy is L3/L4: it cannot say "only GET /api"). That's why mTLS, JWT and the WAF exist on
top, and why port-forward requires cluster-admin-level RBAC.

### Q4. ticket-service has a read-only root filesystem but the WAF doesn't. Why, and how would you fix the WAF? ★★★
**30-second headline:** The WAF image writes rendered config at start; ticket-service needs only /tmp. Fix the WAF with an init container or a baked image.
**Weak answer (what fails):** "Read-only root FS breaks everything."
**Strong answer:** Spring Boot only needs `/tmp` (mounted `emptyDir`). The WAF image renders templates
into `/etc/nginx` and copies rule files into `/etc/modsecurity.d` at startup. Fix: render in an init
container into `emptyDir` volumes mounted at those paths, or bake a final config into a derived image;
then `readOnlyRootFilesystem: true`.

### Q5. `disableNameSuffixHash: true` in kustomize: what operational bug does it introduce? ★★★★
**30-second headline:** Without hash suffixes, changing a generated ConfigMap/Secret doesn't restart pods, so new values are ignored; use hashes, checksum annotations or a reloader.
**Weak answer (what fails):** Not knowing why pods didn't pick up a change.
**Since implemented:** generated Secrets are gone; credentials now come from OpenBao via External Secrets.
**Strong answer:** With hash suffixes, changing a generated ConfigMap/Secret changes its name, which
changes the pod template, which triggers a rolling restart. Disabled, the content changes **in place**:
pods consuming it via `envFrom` keep the old values until restarted (files from volumes update
eventually, `subPath` mounts never do). So a password change "applies" but nothing uses it. Here it is
disabled because scripts reference fixed names; mitigation: a checksum annotation on the pod template
(as the WAF's `ticketing/config-version`) or Reloader.

### Q6. Probes: why TCP for ticket-service, and what's the risk? Design better probes. ★★★★
**30-second headline:** The kubelet can't present the mTLS client certificate, so probes moved to a separate plain-HTTP management port with liveness (no DB) and readiness (with DB).
**Weak answer (what fails):** Liveness checking the database (restart storms).
**Since implemented:** implemented (port 9090, /actuator/health/liveness and /readiness).
**Strong answer:** Tomcat requires a client certificate (`client-auth: need`), and the kubelet can't
present one, so an HTTPS probe fails the handshake. TCP only proves the port is open: a deadlocked app or
lost DB connection still looks healthy. Better: Spring Boot Actuator on a **separate management port**
without mTLS, exposing `/actuator/health/liveness` and `/readiness` (readiness includes DB checks;
liveness must not, to avoid restart storms when the DB is down), protected by NetworkPolicy to the node.

### Q7. Zero-downtime rollout for a single-replica Deployment: is it possible? ★★★★
**30-second headline:** maxSurge 1 / maxUnavailable 0 starts the new pod first, so the gap is endpoint propagation; true HA still needs ≥ 2 replicas and a PDB.
**Weak answer (what fails):** "Impossible with one replica" or "zero downtime guaranteed".
**Strong answer:** With default `maxSurge 25%` (rounded up to 1) and `maxUnavailable 25%` (rounded
down to 0) Kubernetes starts the new pod first and removes the old after readiness, so the gap is only
endpoint propagation + in-flight connection draining. Add `preStop` sleep (5–10 s), graceful shutdown
(`server.shutdown=graceful`), real readiness probes. True HA still needs ≥ 2 replicas + PDB, because
node drains and crashes are not rollouts.

### Q8. Scale this to production on Kubernetes: what changes per component? ★★★★
**30-second headline:** ≥ 2 replicas, HPA, PDB, topology spread, Redis for rate limits, clustered Keycloak, managed databases, policy-as-code and GitOps.
**Weak answer (what fails):** "Increase replicas."
**Strong answer:** WAF/Kong/ticket-service/Keycloak: ≥ 2 replicas, HPA (CPU), PDB `minAvailable: 1`,
topology spread across zones, resource requests from load tests. Kong rate limits → Redis. Keycloak →
Infinispan clustering. Databases → managed services (or operators: CloudNativePG, Percona). Secrets →
External Secrets. Policies → Kyverno/Gatekeeper enforcing pod security and digests. GitOps (Argo CD /
Flux) for drift control.

### Q9. The ClusterIssuer lets any namespace request any certificate. Exploit and fix. ★★★★★
**30-second headline:** Anyone who can create a Certificate can mint CN=kong-gateway; NetworkPolicy mitigates; fix with namespaced issuers, approver-policy and URI SAN identities.
**Weak answer (what fails):** "Only admins create certificates" without RBAC evidence.
**Would I do it again?** I'd use namespaced issuers from the start; the ClusterIssuer shortcut created this risk.
**Strong answer:** Anyone allowed to create a `Certificate` (or a CertificateRequest) in any namespace
can obtain a cert with `CN=kong-gateway` signed by the trusted CA → passes Tomcat's trust and the CN
pin. Mitigated today by NetworkPolicy (only the Kong pod can reach ticket-service). Fix: namespaced
`Issuer` in `gateway` for the client cert; cert-manager **approver-policy** restricting which names
each namespace may request; pin by SPIFFE-style URI SANs; RBAC on cert-manager CRDs.

### Q10. Secrets in this cluster: list every weakness and the production remedy. ★★★★
**30-second headline:** Locally now: random credentials in OpenBao, synced per namespace by External Secrets; remaining: etcd encryption at rest and dynamic database credentials.
**Weak answer (what fails):** "Kubernetes Secrets are encrypted."
**Since implemented:** demo credentials removed from Git and rotated on 2026-10-05.
**Strong answer:** Demo values in Git (**accepted gap** for the laptop); stored base64 in etcd without
encryption at rest (k3s supports `--secrets-encryption`); readable by anyone with `get secrets` in the
namespace; injected as env vars (visible in process env, crash dumps). Remedy: External Secrets
Operator + cloud secret manager, etcd/KMS encryption, files instead of env where possible, rotation
procedures, short-lived DB credentials (Vault database engine / RDS IAM auth).

### Q11. k3d specifics that would surprise someone moving to EKS. ★★★
**30-second headline:** Masqueraded client IPs, kube-router policies, local-path storage, single node, and Windows API binding quirks; each has an EKS equivalent to plan for.
**Weak answer (what fails):** "It's all Kubernetes, it's the same."
**Strong answer:** klipper-lb (`svclb-*` pods) implements LoadBalancer with iptables masquerade →
client IPs lost; kube-router enforces NetworkPolicy (on EKS: VPC CNI network policy feature or
Calico/Cilium); local-path storage (node-local, no replication); single node (no zone spread); API
server address/host mapping quirks on Windows (`--api-port 127.0.0.1:6550` fix in `up.sh`).

### Q12. Rapid fire
* Which pods can reach PostgreSQL? → ticket-service and Keycloak (cross-namespace), nothing else.
* Can a pod call the Kubernetes API? → no token mounted (`automountServiceAccountToken: false`); default SA has only self-review rights.
* Renewal time of a 90-day cert? → after 60 days (2/3).
* Why headless Services for the databases? → StatefulSet stable DNS (`postgres-0.postgres…`).
* What makes the WAF restart after a rule change? → bumping `ticketing/config-version` (subPath mounts don't update).
